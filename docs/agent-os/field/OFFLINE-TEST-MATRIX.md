> **Objetivo:** clasificar los 27 escenarios offline por la evidencia más fuerte que existe HOY, con las suites corriendo en verde.
>
> **Clasificaciones:**
> - **AUTOMATED VERIFIED** — un test real (que importa/ejecuta código de producción) asegura el comportamiento y corre verde ahora.
> - **LAB VERIFIED** — verificado ejecutando algo ahora (traza de código + simulación/corrida manual), pero sin test durable que ejecute el código de producción end-to-end.
> - **PHYSICAL FIELD PENDING** — requiere hardware real / AMALAY (o el path de producción existe pero ningún test lo ejecuta).
>

Sus asserts documentan el algoritmo esperado pero no protegen el archivo real. Donde es la única evidencia, NO se clasifica como AUTOMATED VERIFIED. ## Hallazgos (el código NO hace lo que se asume)

1. **P0 potencial — drain PER-01 genera items imposibles de sincronizar.** `saveOrder` en su fallback de emergencia a localStorage (`pos-data.ts:1413-1415`, cuando IDB falla) encola `{ table, data, endpoint:'/api/pos/save-order', transport:'APP_API' }` **sin campo `method`**. `drainLocalStorageToIdb` (`pos-offline-db.ts:889`) le asigna default `method: 'PATCH'`. Pero `/api/pos/save-order/route.ts` solo exporta `POST` (:34) → el replay PATCH devuelve 405 → `replayViaAppApi` (:404-412) lo clasifica `TRANSIENT_RETRYABLE` → reintento infinito con backoff que **jamás puede tener éxito**. La orden (potencialmente un cobro) queda varada en la cola para siempre — viola en la práctica los escenarios 26/27 en su path de emergencia. Fix trivial: default `'POST'` cuando `transport==='APP_API'`/endpoint `/api/`, o incluir `method:'POST'` en el push de `pos-data.ts:1414`. (No se tocó código de producción en esta tarea.)
2. **Test obsoleto que documenta comportamiento retirado.** `pos-offline-resilience.test.ts:565` "items with retries >= 5 should be skipped" afirma el skip-para-siempre pre-PRR-02 usando un filtro inline (no importa producción). El comportamiento real (`shouldAttemptSync`) es lo contrario: nunca abandona transitorios. Verde engañoso — conviene borrarlo o reescribirlo contra producción.
3. **Cobertura replica vs producción.** Todo `pos-offline-resilience.test.ts` (200+ asserts) reproduce la lógica inline; un refactor en producción no rompería estos tests. Las clasificaciones de esta matriz ya lo descuentan.
4. **Fingerprint mid-session edge (menor).** Si el servicio de huella muere DESPUÉS del health-check del mount, un login por PIN exitoso desemboca en la pantalla de registro de huella (`layout.tsx:419-427`) en vez de entrar directo; el operador debe tocar "Saltar por ahora". No bloquea (verificado + test nuevo), pero es fricción evitable: bastaría re-chequear `/health` antes de mostrar el registro.
