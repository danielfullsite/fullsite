| ID | Riesgo | Severidad | Probabilidad | Evidencia | Entidades afectadas | Mitigación propuesta |
|---|---|---|---|---|---|---|
| R-01 | **CLIENT_ID hardcodeado** — `migrate-wansoft-to-supabase.py` line 22: `CLIENT_ID = "amalay"`. Todos los INSERTs generados llevan `client_id = 'amalay'` sin posibilidad de parametrización. | CRÍTICO | CONFIRMADO | `scripts/migrate-wansoft-to-supabase.py:22` | pos_suppliers, pos_recipes_old, pos_inventory_products | Convertir a parámetro CLI: `python migrate.py --client=atope`. Requiere también que los JSONs de input sean por-cliente. |
| R-02 | **Fields corridos en proveedores** — El scraper de proveedores captura las columnas del portal en el orden equivocado. `"rfc"` JSON = nombre real, `"nombre"` JSON = RFC. El script de migración compensa con heurísticas, pero el problema está en el origen (scraper). | CRÍTICO | CONFIRMADO | `scripts/migrate-wansoft-to-supabase.py:53-66`: "Los campos del scraper están corridos". `agents/wansoft/wansoft_proveedores.json:1-8`: campo `"rfc": "CAM240411880"` contiene el código de proveedor, no un RFC. | pos_suppliers | Corregir el scraper en origen, no compensar en destino. Hasta entonces, validar que el RFC resultante pasa regex antes de insertar. |
| R-03 | **65% de rechazo en dry-run** — Al correr el pipeline TypeScript con datos reales (`--real`), 1456 de 2225 registros fueron rechazados con error. El sistema de validación tiene lógica correcta pero los datos Wansoft no pasan las validaciones actuales. | ALTO | CONFIRMADO | `scripts/migration-pipeline/dry-run-report.json`: `"total_records": 2225, "rejected": 1456`. Los errores son `orphan_references` (ingredient_id no encontrado en catálogo). | recetas, ingredientes | Resolver la causa raíz: el `ingredient_id` se genera con `slugify(product_name)` pero los IDs de ingredientes se generan con `slugify(nombre)` — si los nombres difieren ligeramente, el join falla. Agregar un paso de fuzzy matching. |
| R-04 | **Sin source_id en ninguna tabla de destino** — Los datos migrados de Wansoft (`pos_suppliers`, `pos_recipes_old`, `pos_inventory_products`) no tienen campo `source_id` ni `source_system`. No hay forma de saber cuál registro vino de Wansoft ni cuál fue creado en Fullsite. | ALTO | CONFIRMADO | DDL en `scripts/sql/migrations/001_core_schema.sql` revisado — no hay columnas `source_id` o `source_system` en estas tablas. | pos_suppliers, pos_recipes_old, pos_inventory_products, cualquier tabla futura | Agregar migration SQL: `ALTER TABLE pos_suppliers ADD COLUMN source_system TEXT; ADD COLUMN source_id TEXT; ADD COLUMN migrated_at TIMESTAMPTZ;`. Idem para pos_recipes_old, pos_inventory_products. |
| R-05 | **Sin rollback en ningún flujo** — Ni el backfill de ventas, ni el sync de inventario, ni el SQL generator tienen mecanismo de deshacer. Si se sobreescribe data correcta con data errónea, no hay proceso de restauración automática. | ALTO | CONFIRMADO | Ningún script tiene función `rollback()` o guarda estado previo. Los UPSERT borran la versión anterior. | wansoft_daily, pos_inventory_products, pos_suppliers, pos_recipes_old | Para wansoft_daily: guardar `previous_row` antes del UPSERT. Para SQL generator: generar también `ROLLBACK.sql` con los valores anteriores (requiere SELECT antes del INSERT). |
| R-06 | **Float para dinero** — `parse_num()` convierte montos a Python `float`. Los valores monetarios acumulados en float pierden precisión. Ejemplo: `8843.07` en `wansoft_existencias.json` es float, y cálculos como `value/stock` amplifican el error. | ALTO | CONFIRMADO | `wansoft_backfill.py:48`: `return float(str(s).replace...)`. `migrate-wansoft-to-supabase.py:275`: `cost_per_unit = round(value / stock, 2)`. | ventas_dia, stock, cost_per_unit, saldo_mxn | Usar `decimal.Decimal` en Python para parseo. En TypeScript, usar `number` solo para display; guardar en BD como `NUMERIC` (ya está correcto en el schema). |
| R-07 | **Escritura directa a producción desde scripts GH Actions** — `wansoft_backfill.py` y otros scripts usan `SUPABASE_SERVICE_KEY` y escriben directamente a tablas productivas sin staging ni dry-run previo. | ALTO | CONFIRMADO | `wansoft_backfill.py:26-30`: `SUPABASE_KEY = os.environ["SUPABASE_SERVICE_KEY"]` + `SB_HEADERS["Prefer"] = "resolution=merge-duplicates"`. No hay tabla de staging. | wansoft_daily, wansoft_data, wansoft_menu_config | Agregar staging table (`wansoft_daily_staging`) con un paso de validación/reconciliación antes de promover a producción. En corto plazo: agregar dry-run flag al workflow. |
| R-08 | **Mapeo por nombre, no por ID** — Los ingredientes en recetas se referencian por `ingredient_id = slugify(product_name)`. Si el nombre cambia (typo, renaming en Wansoft), el join se rompe sin señal de error clara. | ALTO | PROBABLE | `scripts/migration-pipeline/dry-run.ts:66`: `const id = String(raw.id || raw.codigo || slugify(String(raw.name || raw.nombre || '')))`. Los slugs se generan desde el nombre si no hay código. | recetas, ingredientes | Usar siempre el `codigo` (ej. `ABA002`) como `source_id` y construir el `slug` solo para display. En `wansoft_products.json` el campo `codigo` existe y es estable. |
| R-09 | **Unidades incompatibles sin bloqueo** — El sistema puede aceptar una receta con ingrediente en `KG` y otro en `PZ` en la misma preparación sin validar coherencia. La conversión entre dimensiones (`mass` → `piece`) está marcada como `'other'` pero no bloquea el insert. | MEDIO | PROBABLE | `scripts/migration-pipeline/maps/units.ts:66-74`: unidades `BTA`, `paq`, `SOBRE` se mapean a `pz` con `dimension: 'other'` pero el `factor` es `1`. | recetas, pos_recipe_lines | Agregar validación de dimensión por familia de ingrediente. Marcar conversiones `other` como REQUIRE_REVIEW en el ValidationReport. |
| R-10 | **Sin idempotencia en inventory scrape** — `wansoft_inventory_scrape.py` guarda datos usando `save_data(key, data)` a `wansoft_data`. No se verificó si hace UPSERT o INSERT. Si hace INSERT, corridas múltiples duplican datos. | MEDIO | PROBABLE | `wansoft_inventory_scrape.py:57-61`: función `save_data()` no leída completamente. Nombre de la función no sugiere upsert. | wansoft_data | Verificar que `save_data()` usa `Prefer: resolution=merge-duplicates` o busca y actualiza. Si no: agregar lógica de upsert. |
| R-11 | **Schemas inconsistentes entre versiones de existencias** — `wansoft_existencias.json` tiene campos `{codigo, nombre, unidad, departamento, existencia, saldo_mxn}` pero `wansoft_existencias_20260707.json` tiene `{department, code, product, unit, stock, value}`. El script de migración solo lee la segunda versión. | MEDIO | CONFIRMADO | Lectura directa de ambos archivos: distintas keys para los mismos conceptos. `migrate-wansoft-to-supabase.py:243`: solo abre `wansoft_existencias_20260707.json`. | pos_inventory_products | Documentar el schema canónico de existencias y estandarizar todos los snapshots futuros al mismo formato. |
| R-12 | **Zonas horarias ambiguas** — `wansoft_backfill.py` usa `datetime.now(timezone.utc)` para `updated_at` pero las fechas de ventas de Wansoft están en timezone MX (UTC-6). Si se corre el backfill a medianoche, la fecha puede quedar desfasada. | MEDIO | PROBABLE | `wansoft_backfill.py:36`: `TODAY = datetime.now(timezone.utc).strftime("%Y-%m-%d")`. MX = UTC-6, entonces a las 11pm MX todavía es "hoy" en MX pero ya es "mañana" en UTC. | wansoft_daily.fecha | Usar `get_tz(CLIENT)` (ya disponible en `client_config.py`) para calcular la fecha local. |
| R-13 | **Scripts solo funcionan para AMALAY** — `wansoft_backfill.py`, `wansoft_inventory_sync.py`, `wansoft_menu_sync.py` usan `client_config.get_client()` que lee `CLIENT_ID` del entorno. Funciona multi-tenant en teoría, pero los JSONs de `agents/wansoft/` son solo de AMALAY. El pipeline TypeScript tiene `CLIENT_ID = "amalay"` hardcoded. | MEDIO | CONFIRMADO | `migrate-wansoft-to-supabase.py:22`: `CLIENT_ID = "amalay"`. | Todos los flujos de catálogo | El flujo de ventas (backfill) es multi-tenant por diseño. El flujo de catálogo/recetas necesita refactorización para parametrizar el cliente. |
| R-14 | **Recetas sin ingredientes en catálogo (orphans)** — El dry-run identificó `orphan_references` — recetas que referencian `ingredient_id` que no existe en el catálogo de ingredientes. Sin resolver esto, el food cost calculado es incorrecto. | ALTO | CONFIRMADO | `dry-run-report.json`: campo `"orphan_references"` presente con valores. `validators/index.ts:77`: `'Orphan reference — ingredient_id not found in catalog'` marcado como `severity: 'error'`. | recetas, food cost | Paso de reconciliación obligatorio antes de insertar: para cada orphan, buscar en catálogo por nombre fuzzy y confirmar manualmente o marcar como `status: 'unresolved'`. |
| R-15 | **RLS/functions/triggers no incluidos en migrations** — El `MANIFEST.json` documenta 194 RLS policies, 15 funciones y 7 triggers que no están en los archivos SQL generados. Un deploy a un tenant nuevo sin estas policies deja tablas sin protección. | ALTO | CONFIRMADO | `scripts/sql/migrations/MANIFEST.json:84-89`: `"rlsPolicies": 194, "functions": 15, "triggers": 7, "reason": "Bodies not available from information_schema"`. | Todas las tablas del schema | Extraer los bodies con `pg_get_functiondef()` y `pg_get_triggerdef()` y agregarlos a los archivos de migration. |
| R-16 | **Dependencia de una sola persona para execución** — La mayoría de los scripts de migración de catálogo son manuales y requieren que Daniel o alguien con acceso a los JSONs y credenciales los ejecute. No hay documentación de cómo correrlos para un nuevo ingeniero. | MEDIO | CONFIRMADO | No existe README en `scripts/migration-pipeline/`. El `CLAUDE.md` del proyecto documenta el contexto general pero no el proceso de migración paso a paso. | Todos los flujos manuales | Crear `docs/migrations/runbook-catalog-migration.md` con pasos exactos, credenciales requeridas y verificaciones. |
| R-17 | **`wansoft_data` sin schema formal** — La tabla `wansoft_data` se usa como key-value genérico (`data_key`, `fecha`, `data` JSONB) para guardar inventario, almacenes y reorder points. No hay schema documentado para los valores que se guardan bajo cada key. | BAJO | CONFIRMADO | `wansoft_inventory_sync.py:71-78`: `save_wansoft_data(data_key, data)` con keys `inventory_state`, `warehouses`, `reorder_points`, `products_catalog`. Sin typedef. | wansoft_data | Documentar el schema JSON esperado para cada `data_key`. Considerar columnas tipadas en lugar de key-value para las entidades más importantes. |
| R-18 | **Migración no reanudable para catálogo** — Si `migrate-wansoft-to-supabase.py` falla a mitad, no hay checkpoint. El script empieza de cero. Para 745 existencias esto es tolerable, pero para tablas más grandes no lo será. | BAJO | PROBABLE | Código del script no tiene manejo de estado/cursor entre corridas. Solo los UPSERT ON CONFLICT garantizan idempotencia, pero si el script crashea antes de generar el SQL, se pierde el trabajo parcial. | Migración de catálogo | Agregar cursor/offset al generador SQL o dividir en batches pequeños con logging de progreso. |
